
### Browse approved memories

Use `POST /v1/memories/list` with a bearer grant, or run `python -m aiap_core --data-dir DATA list-memories --credential-file GRANT --space space:work --purpose PURPOSE`. Supply the grant's purpose and one authorized space.

The request requires `space_ref` and `purpose`. Optional filters are `level`, `memory_type`, `updated_from` (inclusive) and `updated_before` (exclusive). Supply timezone-aware timestamps. The default levels are M1 and M2. Select M3 explicitly for archived memories. Page size is 1–100, default 20.

Each item contains an ID, revision, level, type, update time and a text excerpt of up to 240 characters. Pass `next_after` as `after` with the same grant, space and filters until it is null. Each page reads current state in ascending memory ID order. New or newly matching IDs before the cursor require a fresh traversal. Records that cease to match are excluded from subsequent pages. Browsing does not record memory use.

Owner decisions accept an optional reason code via `decide --reason`; see `decide --help` for values. Owner review returns the original code after the decision and null for decisions without one. Retrying a completed decision preserves the original reason.

Local Owners can use `set-validity --credential-file FILE --space SPACE --memory-id ID --base-revision N` with either `--expires-at TIMESTAMP` or `--successor-id ID --successor-revision N`. Expiry uses an absolute time including an offset. At that instant the memory leaves search, browse and compiled context. A replacement must be current and in the same authorized space. Owner history keeps the prior revision and the exact replacement reference. Records with the new validity extension require a compatible reader; existing sync and recovery readers reject unsupported extensions.

An Owner can locate records for correction with `list-memories --validity expired` or `--validity superseded`, using the grant's space and purpose. These review modes include M1–M3 by default and return the deadline or replacement reference. To remove a mistaken deadline, use `set-validity --clear-expiry` with the listed ID and current base revision. The change is audited and preserves history. An existing replacement still governs a superseded record.

Embedding scopes can include explicitly named project spaces such as `space:project:export`. Authorized search ranks a vector candidate list and a lexical candidate list from the same eligible snapshot, combines reciprocal ranks (constant 60), and prioritizes exact substrings. Each list contributes up to the larger of 60 and the requested limit plus one. Core rechecks outbound batches and the final snapshot. Cold scans still compute missing embeddings under the provider deadline; timeouts can fall back to lexical retrieval. Vectors are cached in process. Successful fused searches report `fusion=reciprocal-rank` and `lexical_retrieval`.

Use `find-preference-evidence --credential-file OWNER_FILE --space SPACE --query TEXT` to look up observations related to a topic. This reads current M1 preference evidence in the Owner's selected space. It uses the space's configured embedding provider when available and reports lexical fallback in the retrieval diagnostics. Each result retains its own wording, revision and source reference. Its `match_ranks` object gives one-based positions on the semantic and/or lexical candidate lists. A channel appears only when it supplied that record. These positions explain retrieval and carry no judgment about agreement with the proposed preference. Related observations can describe exceptions or opposite preferences. Pass selected IDs to the preview as supporting evidence or counterexamples after review.

For a preview based on a search result, pass `--evidence-revision ID REVISION` alongside `--supporting` or `--counterexamples`. Repeat the option for each version you reviewed. The discovery list also returns `sample_revisions` for its example IDs. If an observation was revised before preview or confirmation, Core returns `E_VERSION_CONFLICT`. Review the updated observation before confirming. Selections supplied only by ID use the current version for preview; confirmation still checks the preview digest.


Use `preference-candidates --credential-file OWNER_FILE --space SPACE` to find repeated M1 preference evidence within one space. The list groups observed or explicit-user records with identical wording after Unicode and whitespace normalization. A group appears when two distinct source references are present. Different references can still describe one incident. Each candidate includes the snapshot time in the enclosing response, record and source counts, and up to 50 example IDs (one per source) for evidence review. Continue with `--after` using the returned cursor. Discovery is read-only.

Before proposing a long-term collaboration preference, the local Owner can use `review-preference-evidence --credential-file FILE --space SPACE --memory-ids ID [ID ...]` to inspect selected current M1 observations. Repeated IDs are counted once. Observations citing the same source reference appear together, including differently worded accounts. Separate references may still describe one incident. The output preserves text and revision for reviewing exceptions and project rules. The command only reads evidence.

Use `preview-preference --credential-file FILE --space space:work --statement "Run a preflight" --condition "Production changes" --exception "Try reversible local experiments directly" --runtime dsh --runtime openclaw` to review a proposed M2 preference locally. Optionally add `--project-rule`, `--supporting ID ...`, and `--counterexamples ID ...`. Owner self-descriptions can be previewed without observations. The preview has no effect on stored memories, approvals or runtime access.

When multiple runtimes cite different source references for the same event, pass `--same-event SOURCE_REF_A SOURCE_REF_B` to both preview and confirmation. Repeat it for other disjoint groups. Each reference must belong to the selected observations. The preview shows the resulting groups, including ungrouped singleton sources, with supporting and counterexample roles preserved. The grouping is included in the confirmation digest and the Owner's stored provenance. It expresses the Owner's assessment of event identity.


To save the reviewed local M2 preference, run `confirm-preference` with the same fields and `--preview-sha256 HASH` from the preview. Core rechecks the Owner grant and current evidence in the write transaction. Repeating confirmation returns the existing record. Keep the returned `preference_id` for `withdraw-preference --credential-file OWNER_FILE --space SPACE --preference-id ID`.

Use `recall-preferences --credential-file RUNTIME_FILE --space SPACE --condition "Production changes"` for explicit local recall. Conditions match exactly after trimming surrounding whitespace. The grant determines the runtime. Results expose the statement, condition, exception, confirmation time and ID. A caller should apply a default only when its condition fits and the current instruction allows it. This local registry is separate from ordinary search and the signed memory index. A caller can request these defaults in the same Core context transaction with `context --preference-condition CONDITION` or `preference_condition` on a single-space `/v1/context` request. Set `--skip-preferences` or `skip_preferences: true` for a turn-specific override. Defaults are returned in `preference_defaults`; they are separate from acknowledged memory objects. Existing callers must opt in.

Use `list-preferences --credential-file OWNER_FILE --space SPACE` to find IDs and archived versions. To rewrite, pass the old ID as `--replaces ID` to both preview and confirmation. The preview reports the predecessor status and before/after values for changed wording, conditions, exceptions, project rules, allowed runtimes, scope, and explicit event grouping in `replacement_review`. When evidence references differ, `replacement_review.evidence_changes` lists their IDs and before/after references, including revisions, sources, and roles. An absent side is null. The comparison exposes reference metadata only. The preview verifies the current space commitment when the preference index is signed. This review data is outside the confirmation digest. Successful confirmation archives the predecessor in the same transaction. A competing edit of that predecessor fails. Withdrawal also archives the version and excludes it from subsequent context requests.

### Preference index compatibility

The local Owner can run `preference-manifest --credential-file FILE --space SPACE` to compute a read-only snapshot digest. The digest covers the avatar, the authorization scope (including its policy revision), and all confirmed, superseded and withdrawn preference records in that space. The output includes the record count and digest. Preference text, runtime names, evidence references and individual IDs stay in the registry.

The v1 hash input starts with canonical JSON for `{profile, avatar_id, scope}` and a single LF byte. In ascending SQLite binary key order, append canonical JSON for `{id, sha256}` and LF, where `sha256` is the canonical JSON digest of the entire stored preference record. Hash that stream with SHA-256. This framing also defines the digest for an empty space. Legacy indexes return `signed: false`. For a signed Core declaring the critical `x-aiap-local-preference-index` extension version 1 after its base extension, the reader requires the reference ID `preference-manifest:<space_ref>`, its current scope, and a matching digest. A successful check returns `signed: true`, the Core revision, and the manifest version. Recomputing the digest alone cannot establish provenance or detect rollback of the entire database.

**Signed writes.** On an already indexed space the writer verifies its previous signed commitment in the write transaction. Confirmation, replacement or withdrawal increments the space manifest version and Core revision once, and signs with the enrolled avatar key. A signing failure rolls back the mutation. Other Core rebuilds verify and preserve the existing commitments. Legacy databases continue to use unsigned preferences. The signed reference carries the space policy, digest and manifest version; preference records stay outside ordinary memory enumeration. Creating a project space on an indexed Core commits its empty version-1 manifest and the new Core revision in the same transaction. Repeating the creation preserves the revision and existing grants. Idempotent confirmation and withdrawal do not advance revisions. After activation, a missing or mismatched commitment must block preference delivery until resolved.

**Reader compatibility.** The compact Core builder verifies signed preference commitments before exporting a new-format space manifest (`x-aiap-local-space-manifest-v2`). Its optional `preference_manifest` field holds the signed reference; `entries` contains memory references. The compact Core signature covers the digest of the entire space manifest. Use `inspect-checkpoint-index --checkpoint FILE --checkpoint-sha256 HEX` on a local POSIX system to inspect a pinned, unexpired checkpoint. The inspector verifies the file pin, enrollment, Core and envelope signatures, and scope bindings. It returns memory and preference-manifest counts separately. A preference count describes signed references, not the contents of an external registry. The command reads only the checkpoint file. Its governance and enrollment digests also drive the local `review-checkpoint` diagnostic comparison. The governance digest includes the signed preference references. Local registration and file review support signed preference references. Sync, live source review and restore still require their supported legacy formats. A legacy reader must reject the critical extension. Enable the new writer only after the required readers support it. Existing unsigned records require an explicit Owner-reviewed baseline before activation. An old signed Core and its matching registry can still be rolled back together; freshness requires an independent witness.

The local `scripts/recovery_guard.py checkpoint` issuer reads the signed Core, space policies, memory rows and preference registry in one SQLite snapshot. For a Core with the preference-index extension it recomputes every signed preference manifest and checks that their counts cover the entire registry before signing. The file carries the signed manifest references. Preference bodies remain in the source database. Register and review return separate memory and preference-manifest counts. Registering a newer checkpoint advances the registry head. In this version an indexed head can be reviewed locally, while live source review and isolated restore reject the extension before contacting the source.

To compare a pinned checkpoint against the local source, use `--data-dir DIR compare-local-checkpoint --credential-file OWNER_FILE --checkpoint FILE --checkpoint-sha256 HEX` on POSIX. This requires a current Owner grant for all spaces. Core reads one database snapshot and compares enrollment, signed Core, spaces, tombstones and revocation epoch. For the preference-index extension it recomputes the registry commitments and requires every preference row to be covered. The result reports counts and whether the registry was checked. It reads neither private signing keys nor memory bodies and emits no observation signature. A local match describes the snapshot read by this command.



Run `preview-preference-baseline --credential-file OWNER_FILE` on a legacy local Core to review enrollment inputs. The credential must cover all spaces. The command returns the signed Core digest and revision, each scoped preference digest and count, and the digest of the combined baseline. The response also reports per-space counts of confirmed, superseded and withdrawn records in `status_counts_by_space`. Pass the previously reviewed digest as `--expected-sha256 SHA256` to check it against the current snapshot. A mismatch returns `E_VERSION_CONFLICT`. This read-only review neither establishes the historical authenticity of unsigned preferences nor activates the extension. Production activation remains pending support for the preference registry in the recovery path.

Use `preference-history --credential-file OWNER_FILE --space SPACE --preference-id ID` to read a single preference and its earlier versions, newest selected version first. Each page includes the recorded evidence revisions, confirmation time and lifecycle status. Pass `next_preference_id` as the next starting ID until it is null. The default page size is 20, and `--limit` accepts 1–100. Each page checks the current Owner grant and reads the selected space in one transaction.

Add `--check-evidence` to compare each saved evidence revision with the current eligible M1 in the same space. Results report `current`, `revised`, or `unavailable` and omit observation text. This review is read-only. The Owner decides whether to revise or withdraw the preference.

Owners can find confirmed preferences with changed evidence or authorization scope using `list-preferences --credential-file OWNER_FILE --space SPACE --needs-review`. A result with `scope_changed: true` was confirmed under an earlier scope and requires Owner confirmation of a replacement under the current scope before it can be recalled. Each page examines up to `--limit` confirmed preferences in ID order and reports revised or unavailable M1 references in the current scope, including their original roles as supporting evidence, counterexamples, or both. Continue with `--after` until `next_after` is null, even on an empty page. Each page uses current state; restart the scan to include earlier IDs that changed. Inspect a match with `preference-history --check-evidence` before deciding whether to revise it.

For multiple defaults with the same condition, `recall-preferences --limit N` returns `next_after` when another page exists. Pass it as `--after` with the same grant, space and condition. On `context`, use `--preference-after` with the returned `next_preference_after`. Every request rechecks current authorizations and preference state. A context continuation produces a fresh context view; its cursor applies only to the preference list.
