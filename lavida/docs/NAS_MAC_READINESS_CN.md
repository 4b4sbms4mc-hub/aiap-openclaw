# NAS Core / Mac 见证接入前核对

作者：Wang Lu。2026-11-09。当前只准备部署与核对工具，没有实现或启动跨设备见证服务，没有改动既有NAS容器。具体设备地址、用户名、卷路径、SSH指纹和实际诊断报告留在用户私有工作区，不进入公开仓库。

## 先核对实际运行基线

镜像或软件版本标签相同，不足以说明实际程序和Schema一致。`scripts/inspect_core_public.py` 只读取固定允许清单中的Core程序/公共Schema及清单文件，输出SHA256；未知文件不扫描内容，符号链接和非普通文件拒绝，单文件上限1MiB。示例状态文件不收集。

数据库使用 `mode=ro`、`query_only` 和只读事务，仅查询sqlite_master的Schema元数据并输出整体摘要和对象数，不选择memories/grants等应用表的行，不读取环境变量、凭据、Owner/Avatar私钥或备份，不创建缺失数据库。数据库忙、不可读或损坏时返回不可用状态，不能据此认定数据为空。源码/Schema指纹匹配也不等于确认记忆内容、身份、当前授权或完整恢复合规。

4项只读测试：真实临时Core的只读前后文件不变且输出不含记忆/候选ID/token；缺失数据库不创建、数据库符号链接拒绝；未知文件不哈希、公共文件符号链接拒绝。加97项恢复治理测试，scripts/tests共101项。

本机调用（只适用于已准备的合成环境）：

```sh
PYTHONPATH=lavida/core python scripts/inspect_core_public.py --data-dir /isolated/core
```

实际NAS通过用户在可信终端执行私有包装脚本，使用现有容器内的Python；只流入检查脚本，不复制Core状态。生产容器、数据卷、凭证及插件保持原状；不改变Docker socket/组权限，不为方便诊断开放Core端口。

## 跨设备职责草案

NAS保留Core正文、Owner/Avatar私钥和既有grant。Mac只取得获准治理检查点元数据，独立保管见证私钥和已见头；不能把Mac私钥放进NAS SMB共享，也不能把历史备份目录当作活跃源卷。

正式接入仍需认证通道、来源/范围校验、远程pending与提交幂等、Mac安全密钥托管和轮换、控制丢失恢复、激活前复核及后续撤销。现有同机flock实验不能直接改为跨设备共享锁。

必须明确Mac休眠/断连时的策略：严格同步确认可能阻塞NAS相关治理写入；保持NAS独立运行则需另设计源端持久化状态与恢复时的新鲜性校验，不能当作已实现的等价保证。当前部署准备不会悄悄改变NAS日常读写可用性；Mac不可用时不能自动放行恢复。

用户现已确认选择 NAS 日常读写继续、缺少新鲜证明时拒绝恢复验证。修正过滤条件后的 NAS Schema 对象数及摘要已通过用户重新采集确认，与基线一致；实际指纹及路径仍保留在私有记录中。下一步采用[恢复时实时核对隔离实验](RECOVERY_AVAILABILITY_CN.md)，不把同机同步实验直接作为该策略的生产实现。

## Schema内部对象前缀修正

收尾复核发现 `name NOT LIKE 'sqlite_%'` 中的下划线是SQL通配符，会错误排除合法自定义表（例如 `sqliteXextra`）。这会削弱未知Schema拒绝和只读指纹完整性。现统一改为 `name NOT GLOB 'sqlite_*'`，只排除字面量 `sqlite_` 前缀的SQLite内部对象；恢复工具和持久化reader的Schema检查同步修正。

新增回归证明类似内部名称的自定义表会改变采集摘要，并被恢复工具拒绝；reader原未知表用例也改为该名称。当前101项通过。早期NAS的程序/公共Schema文件核对仍有效，数据库Schema应由修正后的采集器再核对，不能用旧过滤条件的结果排除这类对象。本修正属于当前验收必要收尾，不是低额度期间开启的新功能。
