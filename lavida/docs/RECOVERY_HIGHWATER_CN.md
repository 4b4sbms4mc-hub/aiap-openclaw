# 恢复端已见头持久化实验

作者：Wang Lu。2026-11-09。`scripts/recovery_highwater.py` 在受信本地文件系统上保存恢复端已验证的见证头，补齐[合成见证](RECOVERY_WITNESS_CN.md)恢复端重启后丢失序号的问题。它仍是仓库实验工具，不是见证服务、源事务栅栏、生产激活接口或 Secure Transfer；Core 0.2.0 / 插件 0.3.5 源码候选版本不变。

## 契约和信任

`DurableWitnessReader.enroll(state_dir, reader, proof, expected_head_sha256)` 是显式首次登记。操作者须在备份之外独立取得可信 Avatar、enrollment 摘要、见证公钥、generation 和初始头 SHA256；随机挑战证明通过原验证器后，初始头须与独立 pin 完全一致。不能从不可信备份自动复制信任材料。实验不创建网络服务，不保存 Owner 私钥、记忆正文或 token；保存的见证元数据仍敏感。

状态目录必须是独立受控位置，不应纳入待恢复备份。目录独占创建为 0700，SQLite 文件为 0600；打开时检查当前用户归属和权限，拒绝最终目录/数据库符号链接。宿主文件系统、路径祖先及同一用户运行环境须可信；这不对抗同用户恶意程序、管理员替换路径或设备整体回退，也不证明目录位于另一台设备。

正常构造使用 `mode=rw`，不会因文件缺失重建空库。丢失、损坏、未知表/Schema、登记信任不匹配、历史证明签名失败均拒绝；不能通过重新登记同一目录来清除已见序号。首次登记中断可留下空或已提交目录；不报告成功，也不自动删除/覆盖。操作者应核对残留，必要时显式打开已提交状态检查，而非静默重建。

保存的是完整已验签证明。重读时按证明签发时间验证历史签名，目的仅为认证已见头；不把该历史证明当成当前新响应，也不会因为证明过期就遗忘已知序号。每次新的验证仍须提供匹配本次 nonce、当前时间有效的新证明。

## 提交顺序

每次 `verify` 消耗一次挑战，然后执行 SQLite `BEGIN IMMEDIATE`。持有写锁后重新读取已提交记录，用最新已见头验证新证明，写入新证明并 `COMMIT`；SQLite 使用 `synchronous=FULL`。只有提交成功且返回前证明仍有效，才返回检查点 pin。验证/写入失败回滚、不返回 pin；若提交已完成但终端中断或证明刚好到期，新序号保留，不能为重试而退回旧序号。

每个进程使用独立 reader 实例；同一实例不支持并发线程。不同进程通过 SQLite 写锁串行化，晚验证的旧证明不能覆盖已提交的新头。等待锁有 5 秒超时，超时或 I/O 失败按失败处理，不能退回旧内存缓存绕过数据库。

显式登记提交后请求目录 fsync，常规验证依赖 SQLite 提交语义。真实测试覆盖进程 SIGKILL，不证明断电、磁盘固件、所有文件系统或网络挂载的持久化保证。任何存储不确定性都不得作为“可安全激活”的依据。

## 验收

16 项新增持久化测试，加原 22 项恢复和 16 项合成见证测试，共 54 项本地通过：

- 真正新 Python 进程重启后拒绝旧签名头；持久化 pin 接入实际隔离 SQLite 恢复，源快照保持不变。
- 两个进程都在旧序号时打开，先执行者持写锁，旧证明进程等待；新头提交后旧进程重读最新状态并拒绝回退。
- 在提交前/后 barrier 强制终止真实子进程，重启分别看见上次已提交的旧头/新头，无部分状态。
- 提交异常不返回 pin、回滚并消耗 nonce；提交过程中证明到期时不返回 pin，但已提交高水位保留。
- 初始独立 pin 错误、重复登记、登记目录 fsync 失败、缺失库、损坏库、未知 Schema、信任变更、签名篡改、宽松权限、符号链接均按约定拒绝或保持已提交状态；过期历史证据仍保留已见序号。

其中一项为明确的限制负例：完整恢复端状态库被替换为旧副本，且见证本身回退到旧头时，仍会接受旧的有效签名状态。此工具不具备受信外部单调存储，不能声称解决整体存储回滚。源端绕过 pending 的负例也仍成立。

重现（仓库根目录，Python 3.12 和 Core requirements）：

```sh
python -m unittest discover -s scripts/tests -v
```
