# 源治理事务与见证发布隔离实验

作者：Wang Lu。2026-11-09。`scripts/recovery_source_gate.py` 实现同一受信 POSIX 主机上的源事务/见证协调实验。现有生产 `Service`、HTTP、Gateway 和 NAS 配置未接入实验；Core 0.2.0、插件 0.3.5 源码候选及既有发布资产不变。这不是跨设备分布式事务、独立见证服务或生产恢复承诺。

## 适用入口与状态

只有显式创建的 `ExperimentalGatedService(gate)` 参与协调。初始化仍由独立 Core 完成，再用 `SourceGate.enroll` 指定当前签名检查点及独立 pin 登记。检查点须对应实际当前源状态；不能用旧检查点和旧 pin 登记当前新源。后续打开必须提供原先登记的 Avatar/enrollment/generation/见证公钥信任材料，缺失或损坏状态不自动重建。

控制目录不能与 Core 目录互相包含，使用 0700 目录、0600 锁文件、原子替换的状态文件和检查点。状态保存合成见证的私钥、generation、已发布头、pending 标记和源路径绑定，支持进程重启继续拒绝未完成更新。**私钥在实验状态文件中明文保存**，仅供临时合成测试；真实见证的安全密钥托管、轮换和丢失恢复尚未实现，不能将控制目录当可迁移业务状态导出。同一主机的不同目录不构成独立信任来源。

所有实验 Service 事务持同一 POSIX flock，比较事务前后的 Core、spaces、tombstones、revocation epoch 摘要，并独立检查实际 enrollment / Avatar / Owner 绑定。批准、删除、撤销、访问确认以及归档的相关状态变更都触发更新。会话/搜索、只增加视图、签发 grant、提出或拒绝候选不改变当前检查点语义时，不推进见证序号；它们的既有授权校验和 SQLite 事务仍保留。

## 提交顺序与拒绝规则

1. 持写锁，重读控制状态，确认无 pending，实际源摘要与已发布头一致。
2. 在 Core SQLite 事务中执行既有服务方法，检测治理变化。
3. 在源事务提交前，先将 pending 和当前见证身份/头原子写入控制状态，并请求文件及目录 fsync。保存失败时源事务不提交。
4. 提交 Core SQLite。此后导出真实已提交源的签名检查点，生成新见证头，再持久化新头并清除 pending。
5. 只有完成最后发布后，实验服务方法才能正常返回。期间 `answer` 非阻塞尝试同一锁，锁忙或 pending 时拒绝证明；重启仍读取原 pending，不能退回旧头。

`answer` 同时在源 SQLite 事务内核对实际 enrollment 和治理摘要，并重新校验所选检查点。直接用原 `Service` 修改源时，下一次检查可发现摘要不一致并拒绝；但这些绕行写入不参加 flock，因此不能保证它们在证明返回后的竞态被阻止。正式接入前必须覆盖所有入口，不能以这个检测代替强制拦截。

## 失败恢复与幂等

源提交前中断：SQLite 回滚源变更，但已保存的 pending 保留。源提交后、见证发布前中断：源变更已生效，pending 保留，拒绝证明。最终头已保存但调用方未收到返回：新头已生效，不能盲目重做源变更。

`resync()` 只在写锁下从**实际已提交源**重新导出检查点；不接受调用方提供的旧检查点参数，也不重新执行删除/批准等原动作。无 pending 且摘要一致时仅返回已发布头，重复调用不增加序号。无 pending 但发现源摘要不一致时拒绝，不能静默把绕行操作或回退宣布为已协调。

检查点导出后、头发布前失败可能留下未发布文件；恢复只相信控制状态指向的文件，不能扫描目录选择“最新文件”。未发布检查点、SIGKILL 遗留临时文件和历史检查点不自动激活或清理；清理/容量策略待后续设计。过期检查点拒绝证明，`resync()` 不自动续期 ready 状态。后续[显式安全续期](RECOVERY_RENEWAL_LOSS_CN.md)提供 `refresh(expected_sequence)`；仍未建立后台刷新任务。

调用抛出异常**不等于源操作未发生**。应先检查实际已提交源和控制状态，必要时显式 resync；避免在未知结果下重复提交有实质后果的动作。控制存储和源存储需要可靠的本地文件系统；真实进程终止测试不证明断电或所有磁盘/网络文件系统持久性。

## 验证

20 项源栅栏测试与原有 54 项恢复相关测试合计 74 项本地通过：

- 当前检查点登记、独立见证证明、持久化 reader、旧快照实际隔离恢复形成闭环，已删除记录不重新出现。
- 批准、删除、撤销、访问确认、归档都推进相应头；纯读取/非治理变化不误推进。
- pending 保存失败阻止源提交；pending 后 SQL 回滚、源已提交/检查点导出失败、头已发布后响应失败均按上述规则恢复，重复 resync 不重复源变更。
- 四个提交边界分别 SIGKILL 真实子进程；新进程保持 pending/已发布头，重新同步的结果对应真实已提交源。两个真实写进程并发删除不同记录，最终头保留两项删除，无序号覆盖。
- 控制状态缺失/损坏、信任变更、私钥与固定公钥不匹配、宽松权限及符号链接拒绝；实际 enrollment 变化也拒绝，不能只检查 Core 摘要。

明确限制负例：完整源数据库和控制状态一起回退时，新 reader 仍可能接受旧有效签名状态；保留更高已见序号的 reader 会拒绝。源返回证明后的新变化也没有持续传播/激活租约保证。尚无跨设备认证、远程见证、密钥轮换、全入口生产接入或安全控制权转移。
